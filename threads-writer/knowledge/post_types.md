# Типы постов и правила интеграции URL

> URL источника нужен НЕ ВСЕГДА — только для определённых типов постов. Автоматом лепить ссылку к каждому посту — засорять ленту и делать посты «служебными» вместо цепляющих.

> 🔴 **Режим Ward (по умолчанию): внешних ссылок нет.** Красная линия ToV Ward — против теневого бана в тексте поста нет внешних ссылок. Переключатель — `config/settings.yml` → `links.external_links_allowed` (сейчас `false`). Пока он `false`, у ВСЕХ типов ниже URL не ставится: там, где методика требует URL, источник **называется словами** («в свежем отчёте одной из крупных бирж», «в разборе ликвидаций за сутки»), а сам пост должен быть понятен без клика. Правила ниже остаются методикой на случай, если клиент разрешит ссылки.

Принцип методики: *URL нужен, только если пост построен вокруг конкретного свежего продукта/репо/инструмента. Если пост — авторский тезис, URL не нужен.*

---

## Каждый пост имеет ОДИН тип

При генерации модель мысленно (или явно, если формат структурированный) присваивает посту тип. От типа зависит поведение URL, длина, тон, наличие CTA.

### `hype-launch` — «срочно посмотри», новый релиз, свежий инструмент
**Триггер типа:** пост построен вокруг **свежего конкретного продукта/инструмента/события**. Тонкие маркеры: «срочно», «вышло», «завтра это будет у всех».

**Примеры хука (Ward):**
- «В терминалах появилась штука, которая подсвечивает плотности прямо на графике. Новичкам стоит знать, что она показывает и чего нет»
- «За сутки на рынке ликвидировали тех, кто зашёл с плечом x20. Вот что в этот момент было видно в стакане»

**Правило URL:** 🔴 **обязательно, если `external_links_allowed: true`**. При `false` (Ward) — без URL, предмет описан словами так, чтобы читатель понял его без клика (иначе пост — сирота, см. `standalone_context.md`). Конкурентов, брокеров и биржи по имени не называем.

**Формат (если ссылки разрешены):** URL отдельной последней строкой, без лейбла «Источник:». Threads сам сделает превью.

### `author-thesis` — авторский тезис (переупакованная мысль из источника)
**Триггер типа:** пост НЕ упоминает конкретного продукта/автора, работает как **чистая мысль от автора**. Источник — топливо, но не рамка (см. `atomic_posts.md`).

**Пример хука:**
- «Не суди тренд по последней свече»
- «Стратегии без минусов не существует. Профи теряет мало и по плану»

**Правило URL:** ❌ **не нужен**. Пост принадлежит автору, ссылка тут выглядит как «взял с чужого материала» → размывает голос.

### `personal-take` — авторская позиция от «я»
**Триггер типа:** пост начинается или строится вокруг личного опыта («первый год закрывался на дне каждого отката», «сидел у стакана и понял»).

**Правило URL:** ❌ **не нужен**. Личный опыт не нуждается в подтверждении ссылкой. 🔴 Личный опыт — только реальный (из источника или подтверждённый пользователем), не выдуманный.

### `data-punch` — цифра как хук/панч
**Триггер типа:** в посте центральная цифра/стат/факт из источника («95% новичков…», «плечо x20 и −60% за 10 минут»).

**Правило URL:** 🟡 **желательно, если цифра из конкретного отчёта/статьи** и ссылки разрешены. При `false` — источник назвать словами («по данным биржевой статистики за сутки»). Цифра никогда не подаётся как обещание дохода.

### `source-quote` — цитата известного автора/эксперта
**Триггер типа:** пост построен вокруг цитаты («как писал Марк Дуглас в книге про психологию трейдинга…»).

**Правило URL:** 🟡 **желательно** при разрешённых ссылках. В любом случае применяется `ТЕСТ 2.5` из `standalone_context.md`: имя автора требует объяснения, кто это.

### `cta-subscribe` — CTA-пост с призывом подписаться
**Триггер типа:** финальный пост серии, зовёт подписаться. Канонический текст Ward: **«Подпишись, чтобы не потерять»** (допустимы естественные вариации).

**Правило URL:** ❌ **не нужен никогда**. CTA не выпускает читателя из ленты.

**Формат текста:** канонический из `audience_dna.md` (раздел «Призыв к действию»). Курс, Discord, KYC, бесплатные материалы за подписку и кодовые слова в комментариях **пока не продвигаем**.

## 🎯 Как это применяется в потоке

**При генерации:**
1. Для каждого поста мысленно выбираем тип из списка выше.
2. Проверяем `links.external_links_allowed` в `config/settings.yml`. `false` → URL не ставим ни у одного поста, предмет называем словами.
3. Если ссылки разрешены и тип = `hype-launch` → достаём URL из источника, кладём в конец поста.
4. Если тип = `author-thesis` / `personal-take` / `cta-subscribe` → URL НЕ добавляем.
5. Если тип = `data-punch` / `source-quote` → решаем по контексту (цифра из конкретного отчёта? имя нуждается в проверке?).

**Проверка перед сдачей (finale sweep):**
- [ ] Каждый пост — один тип из списка. Микс типов в наборе — норма (`hype-launch` + `author-thesis` + `data-punch` + `cta-subscribe` = разнообразие).
- [ ] URL стоит ТОЛЬКО у типов, где он положен, и только если ссылки разрешены в конфиге.
- [ ] Нет постов без типа (значит либо это `personal-take`, либо пост — «ни о чём», под удаление).

## Как это переводится в матрицу разнообразия

Тип поста = одна из осей матрицы `atomic_posts.md`. Разнообразие типов = разнообразие «стилей общения» в перемешанной ленте.

**Плохо:** 3 поста подряд одного типа `hype-launch` — читатель почувствует, что автор постит только «срочные новости» и не имеет своей мысли.

**Хорошо:** 1 `hype-launch` (событие) + 1 `author-thesis` (мысль) + 1 `cta-subscribe` (финал). Или 1 `personal-take` + 1 `author-thesis`. Или 1 `data-punch` + 1 `author-thesis` + 1 `cta-subscribe`.

**Правило:** ≤ 50% постов одного типа. При 2 постах — оба типа разные. При 3 постах — минимум 2 разных типа.
